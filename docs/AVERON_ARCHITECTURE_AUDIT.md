# Averon Technologies architecture audit

_Audited 2026-08-13. Secret values were not inspected or reproduced._

## Executive summary

The repository began as one npm package: a React 19.2 / React Router 8.2 single-page application built by Vite 8.1 and TypeScript 6.0. It combines the public Averon Technologies site, customer account area, Firebase-authenticated admin interface, and website Emmy assistant. The privileged Firebase Admin, Stripe, and DeepSeek behavior has since moved to the independently runnable `averon-api`; root Vite now contains frontend build configuration only.

The current root application is designated **averon-web** and remains in place to protect its routes, styles, assets, and uncommitted work. The workspace directories establish `emmy-app`, `averon-api`, and shared contracts without moving existing behaviour. In the second migration phase, `averon-api` became authoritative for Firebase Admin initialization, server token verification, server authorization, and the Firestore Admin foundation.

## Current architecture

### Frontend and entry points

- `index.html` → `src/main.tsx` → `src/app/App.tsx` is the sole original entry point.
- Public routes: `/`, `/products`, `/products/:slug`, `/services`, `/technology`, `/technology/:topicSlug`, `/projects`, `/blog`, `/blog/:slug`, `/contact`, payment result routes, and authentication routes.
- Protected customer routes: `/account`, `/account/:section`, and `/client-portal`.
- Admin routes: `/admin/login`, `/admin`, `/admin/homepage`, `/admin/products`, `/admin/projects`, plus routes generated by `src/data/adminConfig.ts`.
- Styling is source-managed under `src/styles`; static assets are in `public`.

### Backend behaviour

`apps/averon-api` owns Firebase Admin authentication/authorization, migrated business APIs, Stripe Checkout/webhooks/reconciliation, and the public Emmy DeepSeek call. Its runtime provides health/readiness/version endpoints, structured operational logging, explicit body/network limits, origin enforcement, and graceful shutdown. No development-only Vite middleware serves active API behavior.

### Authentication and authorization

- Customer and admin login both reuse Firebase Authentication (`src/contexts/CustomerAuthContext.tsx`, `src/utils/adminAuth.ts`).
- Customer protection is client-side routing plus Firebase auth state.
- Admin route rendering depends on Firebase ID-token claims, while Firestore rules are the actual data authorization boundary.
- The new API verifies the same Firebase ID tokens through Firebase Admin. It does not introduce a second identity system.

### Database, storage, email, and knowledge

- Browser-side Firestore access is centralized mostly in `src/services/customerWorkflow.ts`, but includes both customer and privileged admin reads/mutations.
- Collections include users, quotes, contracts, invoices, payments, messages, notifications, and audit logs.
- Firebase client configuration is in `src/lib/firebase.ts`. Firebase Admin initialization is owned by `apps/averon-api/src/services/firebase/admin.ts`. The legacy Vite Stripe plugin temporarily imports that server service rather than initializing Firebase Admin itself.
- Storage paths are only declared in `src/services/foundations.ts`; no Firebase Storage client implementation was found.
- Email templates and provider environment-variable names exist, but no sending integration was found.
- Public Emmy retains a backend-owned static public knowledge string for behavior compatibility. Private Emmy now consumes a deterministic, bounded, role-filtered subset of structured Business OS through an authenticated workspace route; public Emmy does not consume it.
- Private Emmy now optionally routes recommendation/drafting requests through a deterministic central orchestrator. Research, SEO, blog/writing, analytics, and documentation workers are internal, read-only, provider-neutral, dependency-bounded, and invisible to users. Coding, deployment, customer support, email, Altrex, and mutation capabilities remain inactive.
- Worker output is schema-versioned and strongly validated with at most one formatting repair. Authorized private responses can return safe Business OS type/version citations, deterministic fixtures guard routing/isolation, and platform admins can inspect bounded metadata-only in-memory diagnostics.

### Deployment and tests

- No Firebase Hosting, Vercel, Netlify, container, or CI deployment configuration was found.
- The original repository had no test script or checked-in tests.
- `firestore.rules` exists but is untracked and was not modified during this migration.
- Existing production deployment behaviour therefore cannot be inferred safely from this repository alone.

## Security findings

1. **Server boundary established:** Stripe and DeepSeek provider behavior are API-owned. Root Vite configuration contains React build configuration only. Phase 7 documents the provider-neutral production topology, readiness, shutdown, CORS, and scaling constraints; a hosting provider is intentionally not selected.
2. **Direct privileged browser mutations:** admin functions in `src/services/customerWorkflow.ts` create contracts/invoices/notifications, update quotes/messages, and create audit records directly in Firestore. Safety depends entirely on deployed custom claims and Firestore rules.
3. **Tenancy foundation established:** businesses, workspaces, and memberships now provide server-enforced isolation for new workspace APIs. Legacy Phase 4 customer/business records still use `customerId` and are not silently reclassified; their workspace migration remains future work.
4. **Business OS foundation established:** new workspace-scoped sections and decisions are server-only, classified, versioned, validated, and audited. Public website content remains source-managed until a coordinated canonical-content migration is approved.
5. **Client-side admin boundary:** admin navigation/layout protection is not a substitute for server authorization. Firestore rules currently carry this responsibility.
6. **Environment hygiene:** the root `.env` was untracked and the original `.gitignore` did not exclude `.env`. The ignore rules now exclude real environment files while retaining examples. No secret values were copied.
7. **Provider errors:** active API provider errors are mapped to stable sanitized envelopes; frontend bundles contain no provider credentials.
8. **Broad collection helper:** `subscribeCustomerCollection(name, ...)` accepts an arbitrary collection name. Rules mitigate access, but the client API is broader than necessary.
9. **Typed signature/audit data:** contract signatures and user-agent metadata are written directly by the browser. Server-side validation and immutable audit recording should replace this later.
10. **Admin enforcement improved but partial:** the API now enforces the existing `owner`/`admin` custom claim server-side. Legacy browser-to-Firestore admin operations still depend on Firestore rules until each operation migrates.

Phase 4 moved existing privileged admin collection reads, quote replies, contract assignment, contract signing, message state, and associated audit/notification writes behind averon-api. Projects and blog remain source content because no persistent domain exists. Stripe-owned payment writes remain legacy by explicit scope.

`firestore.rules` appears to enforce owner/admin access for legacy listed collections, but production rules were not inspected or changed. New tenancy and Business OS collections have no client allow rules and are accessed only through Firebase Admin in averon-api.

## Hard-coded external URLs

Unsplash image URLs occur in public content; Kita Clean Bavaria links to its live site; footer social links point to generic X and Instagram roots. DeepSeek's endpoint exists only in the server-side provider default.

## Migration blockers

- A production hosting provider and deployment configuration have not been selected; Phase 7 documents the required provider-neutral topology.
- Existing application work is extensively uncommitted, so a physical root-app move would create a high-conflict, hard-to-review diff.
- Production Firebase rules and custom-claim provisioning cannot be verified from local source alone.
- There are no original integration tests for auth, Firestore, Stripe webhook processing, or Emmy.
- Workspace/business tenancy and membership persistence are not defined in Firestore.
- Existing mock account data is interwoven with working UI and needs a separately approved cleanup.
- Email and Storage are contracts/placeholders, not implemented services.

## Phase 7 runtime posture

The centralized API now has separate liveness/readiness probes, safe capability states, startup configuration validation, JSON completion logs, AI/payment operational events, explicit network timeouts and body limits, exact-origin CORS, standard API security headers, and bounded graceful shutdown. The remaining material runtime limitation is the per-instance in-memory rate-limit store. Production credential provisioning, external HTTPS hosting, log collection, and live Firebase/Stripe/DeepSeek verification remain environment-owned and were not performed in the repository.

## Phase 13 grounding audit

Phase 12 citations described relevant Business OS sections but did not prove that an individual generated claim used them. Phase 13 replaces that ambiguity with request-local opaque source references, structured claims, server-side workspace/reference validation, and citations derived only from accepted claims. Invented, unavailable, and cross-workspace references are rejected; unsupported business claims are discarded. Golden fixtures now cover grounding, refusal/uncertainty, tenant isolation, planner selection, and mutation absence. Diagnostics remain content-free and bounded behind a replaceable asynchronous interface; the default store is still process-local.

## Phase 14 capability/readiness audit

Private orchestration now separates requested skill identity from agent identity. The deterministic planner produces registered capabilities, readiness checks local provider/model/tool/schema/certification declarations plus workspace permission and risk policy, and an indexed resolver selects the smallest sufficient ready team before invoking the existing orchestrator. The production registry contains exactly five active AgentSpecs and six skills derived from their existing behavior; 100-definition scale is exercised only in tests. Existing limits remain four specialist tasks, five total provider calls including synthesis, and dependency depth three. No frontend-controlled agent/skill/readiness input, production action right, new tool, new provider, or external integration was added.

## Phase 15 initial-swarm audit

The same production registry now contains exactly 15 enabled AgentSpecs and 16 skills. The ten additions are Frontend, Backend, Database, Testing/QA, Security, Business Operations, Marketing, Sales, Customer Operations, and Critic/Verifier. All remain advisory, tool-free, workspace-authorized, schema-certified, provider-abstracted, and subject to Phase 13 provenance/grounding. Risk rules require independent Critic verification for security/auth/payment/migration and explicit high-impact verification patterns without adding majority voting or universal verifier cost. Execution bounds and public/private separation are unchanged; no mutation or external integration was added.

## Phase 16 swarm-quality audit

Production remains exactly 15 certified read/analyze/draft/recommend specialists. The existing orchestration path now has deterministic stress fixtures, a checked-in failure corpus, structured contradiction metadata, explicit partial-failure/synthesis safety metadata, expanded execution-claim enforcement, safe aggregate diagnostics, and documented overlap/skill-gap evidence. No new agent, tool, provider, mutation right, deployment, or external integration was introduced. See `docs/PHASE_16_SWARM_QUALITY_EVALUATION.md`.
